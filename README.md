# Immune Cell Population Analysis

## Overview

This project analyzes immune cell population data from clinical trial samples to help understand how immune cell composition differs across biological samples and whether specific immune cell populations are associated with treatment response.

The input dataset contains biological sample metadata along with counts for five immune cell populations:

- B cells (`b_cell`)
- CD8 T cells (`cd8_t_cell`)
- CD4 T cells (`cd4_t_cell`)
- Natural Killer cells (`nk_cell`)
- Monocytes (`monocyte`)

The project performs four main tasks:

1. Loads the CSV data into a relational SQLite database.
2. Calculates the relative frequency of each immune cell population for every sample.
3. Compares immune cell frequencies between responders and non-responders among melanoma patients receiving Miraclib.
4. Performs subset analysis on baseline melanoma PBMC samples and answers the requested cohort-level questions.

An interactive Streamlit dashboard is also included to display and explore the analysis results.

# Part 1: Data Management

## Relational Database Design

The original CSV contains two different types of information:

1. Sample-level metadata
2. Immune cell count measurements

Instead of storing everything in a single database table, the data is organized into two related tables:

- `samples`
- `cell_counts`

This reduces unnecessary repetition and makes the data easier to query and extend.

---

## `samples` Table

The `samples` table stores information describing each biological sample.

The table contains fields such as:

```text
sample
project
subject
condition
age
sex
treatment
response
sample_type
time_from_treatment_start
```

The `sample` field uniquely identifies each biological sample and acts as the key used to connect sample metadata with its immune cell measurements.

A single subject may have multiple biological samples, so `subject` and `sample` represent different concepts.

For example, one patient may have samples collected at multiple time points.

---

## `cell_counts` Table

The `cell_counts` table stores the immune cell measurements.

Its main fields are:

```text
sample
cell_type
count
```

The `cell_type` field contains one of the five immune cell populations:

```text
b_cell
cd8_t_cell
cd4_t_cell
nk_cell
monocyte
```

Each sample therefore has multiple rows in this table, one for each immune cell population.

For example:

```text
sample00002 | b_cell      | 9794
sample00002 | cd8_t_cell  | 22940
sample00002 | cd4_t_cell  | 24274
sample00002 | nk_cell     | 17482
sample00002 | monocyte    | 18332
```

The `sample` field connects these measurements back to the corresponding record in the `samples` table.

---

## Why Use Two Tables?

The sample metadata is the same for all five immune cell populations belonging to a sample.

If all information were stored in one table, fields such as:

```text
project
subject
condition
age
sex
treatment
response
sample_type
```

would need to be repeated for every immune cell population.

Separating the metadata and cell measurements reduces this repetition and provides a cleaner relational structure.

It also allows the metadata and measurement data to be queried independently when needed.

---

## Scalability

The database was designed with scalability in mind.

If the number of projects, samples, subjects, or immune cell populations grows in the future, the database can accommodate that growth without requiring major changes to the existing schema.

For example, suppose the current analysis contains five cell populations but future studies introduce additional populations.

Instead of modifying the database structure and adding new columns, the new populations can simply be inserted as additional rows in the `cell_counts` table.

For example:

```text
sample00002 | dendritic_cell | 3500
sample00002 | neutrophil     | 7200
```

The same design can therefore support hundreds of projects, thousands or millions of samples, additional cell populations, and different types of downstream analyses.

For substantially larger datasets, indexes could also be added to frequently queried fields such as sample, project, treatment, condition, response, and time point to improve query performance.

# Part 2: Initial Analysis – Cell Population Frequencies

The first analytical question is:

> What is the frequency of each cell type in each sample?

For each sample, the total cell count is calculated by adding the counts from all five immune cell populations.

For example:

```text
total_count =
b_cell
+ cd8_t_cell
+ cd4_t_cell
+ nk_cell
+ monocyte
```

The relative frequency of each immune cell population is then calculated using:

```text
percentage = (cell population count / total cell count) × 100
```

For example, if a sample contains:

```text
B-cell count = 9,794
Total count  = 92,822
```

then:

```text
B-cell percentage =
(9,794 / 92,822) × 100
= 10.55%
```

The final Part 2 summary table contains:

```text
sample
total_count
population
count
percentage
```

The complete output is saved as:

```text
cell_frequencies.csv
```

# Part 3: Statistical Analysis

The purpose of Part 3 is to determine whether the relative frequencies of immune cell populations differ between patients who respond to Miraclib and those who do not.

The analysis includes only samples meeting all of the following conditions:

```text
condition   = melanoma
treatment   = miraclib
sample_type = PBMC
response    = yes or no
```

The samples are divided into two groups:

```text
Responders     → response = yes
Non-responders → response = no
```

The relative frequency of each of the five immune cell populations is then compared between these two groups.

---

## Statistical Method

For each immune cell population, I used Welch's independent two-sample t-test to compare the relative frequencies between responders and non-responders.

Welch's t-test was used because it does not require the two groups to have equal variances.

The null hypothesis for each population is that responders and non-responders have the same mean relative frequency.

A raw p-value below `0.05` is commonly considered evidence against the null hypothesis.

However, five separate cell populations are tested in this analysis.

Performing multiple statistical tests increases the probability of observing a significant result by chance.

Therefore, the Benjamini-Hochberg False Discovery Rate (FDR) procedure was applied to adjust the p-values for multiple comparisons.

A cell population was considered statistically significant when:

```text
adjusted p-value < 0.05
```

---

## Statistical Results

| Population | Responders Mean (%) | Non-Responders Mean (%) | t-statistic | Raw p-value | Adjusted p-value | Significant |
|---|---:|---:|---:|---:|---:|---|
| b_cell | 9.80 | 10.00 | -1.3688 | 0.171213 | 0.321081 | No |
| cd8_t_cell | 24.88 | 24.94 | -0.2944 | 0.768468 | 0.768468 | No |
| cd4_t_cell | 30.54 | 29.90 | 2.8094 | 0.005013 | 0.025063 | Yes |
| nk_cell | 14.84 | 15.07 | -1.3032 | 0.192649 | 0.321081 | No |
| monocyte | 19.94 | 20.08 | -0.7294 | 0.465844 | 0.582305 | No |

---

## Part 3 Conclusion

After applying FDR correction, `cd4_t_cell` was the only immune cell population with a statistically significant difference between responders and non-responders.

The mean CD4 T-cell relative frequency was:

```text
Responders:     30.54%
Non-responders: 29.90%
```

The adjusted p-value was:

```text
0.025063
```

Since:

```text
0.025063 < 0.05
```

the difference remains statistically significant after correcting for multiple comparisons.

The other four immune cell populations did not show statistically significant differences.

This result indicates an association between CD4 T-cell relative frequency and Miraclib response within the analyzed dataset. It should not, by itself, be interpreted as proving that CD4 T-cell frequency can predict treatment response in new patients. Establishing predictive performance would require additional modeling and validation.

# Code Structure and Design Decisions

The project is divided into separate scripts so that each stage has a clear responsibility.

### `load_data.py`

Responsible for Part 1.

It:

- Creates the SQLite database.
- Initializes the relational schema.
- Reads the input CSV.
- Loads sample metadata.
- Loads immune cell count measurements.

### `analysis.py`

Responsible for Part 2.

It:

- Reads cell-count information from SQLite.
- Calculates the total cell count for each sample.
- Calculates relative frequencies.
- Generates `cell_frequencies.csv`.

### `statistical_analysis.py`

Responsible for Part 3.

It:

- Selects melanoma patients receiving Miraclib.
- Restricts the analysis to PBMC samples.
- Separates responders and non-responders.
- Performs Welch's t-tests.
- Applies Benjamini-Hochberg FDR correction.
- Generates statistical results.
- Generates boxplots.

### `subset_analysis.py`

Responsible for Part 4.

It:

- Identifies baseline melanoma PBMC Miraclib samples.
- Counts samples by project.
- Counts unique subjects by response.
- Counts unique subjects by sex.
- Calculates the requested average B-cell count.

### `dashboard.py`

Provides the interactive Streamlit dashboard.

It displays:

- Cell population frequencies
- Statistical results
- Significant cell populations
- Interactive cell population selection
- Responder vs non-responder boxplots
- Baseline cohort results
- Average B-cell count

---

## Why This Structure?

Separating the project into multiple scripts makes the code easier to understand, test, debug, and maintain.

For example, database loading can be modified independently without changing the statistical analysis code.

Similarly, new analyses can be added without significantly changing the existing data-loading pipeline.

The Makefile connects these components into a single reproducible workflow.
